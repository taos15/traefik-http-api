## Existing implementation and baseline

- Rust 2024, Tokio, Axum, SQLx/SQLite, Bollard, Dioxus web; one deployment. Independent Docker Engines form one logical inventory, not Docker Swarm.
- Docker connections support HTTP proxy, SSH, mutual TLS and Unix socket. Each server separately records Docker API endpoint, Traefik-reachable published-port host and browser-reachable WebUI host. Docker proxy permissions vary.
- SQLite migration/import, real login, server/container management and provider GET `/api/v1/traefikconfig` exist. Traefik polls the GET on the same listener; it is anonymous by default, optionally protected by `PROVIDER_TOKEN`, independent of WebUI login. In the proposed deployment Traefik and app share a Docker daemon and user-defined network; polling should use the app's network name instead of a host IP.
- Provider generation selects running, opted-in containers, produces full upstream URLs, and stores the last complete successful snapshot across Docker discovery failures. Deliberate server disable/deletion removes routes. Dioxus shows inventory, actions, state/host tabs and WebUI links.
- Supported labels include `traefik.enable`, `swag=enable`, `traefik.name`, `traefik.hostname`, `traefik.webuiport` (published **host** port), `traefik.service.scheme`, `traefik.service`, `traefik.http.disable`, `traefik.middlewares`, `traefik.entrypoints`, `traefik.icon`, `traefik.forwardauth`, and deprecated `authelia_auth=false`. Explicit `traefik.middlewares` replaces automatic auth. The extension now generates `http.middlewares` for qualified auth containers; its production validation is still pending.
- The actual Traefik install has file and HTTP providers, an `https` entrypoint with TLS and `default@file`, and an API at `:8080`. It currently uses a legacy-generated `auth@http` chain referencing `oauth@file`; `auth@file` does not exist. The file provider holds `oauth`, `oauth-signin`, `oauth-verify`, `Oauth2proxy`, and other resources. Do not carry `auth@file` forward as a presumed default.

## Proposed extension — design, not implemented

### Ownership and precedence

- Traefik static config owns entrypoints, TLS defaults and provider activation. User-maintained dynamic files are the **primary** definitions. The app's HTTP provider supplies changing container routers/services and, only when needed, its own fallback `default-forward-auth@http` plus supporting middlewares/services. It does **not** write to the Traefik directory. File and HTTP provider namespaces remain distinct.
- A single middleware name, `default-forward-auth`, is the router's **automatic** auth choice. If a valid loaded `default-forward-auth@file` exists, use that reference and the file provider's dependencies exactly as Traefik loaded them: no field-by-field merge and no app-generated replacements for its dependencies. If it does not exist, select one of the app's auth YAML templates when a qualified local auth container exists. An existing `auth@file`, `auth@http` or `oauth@file` is **not** `default-forward-auth`; its presence alone does not prevent generating the default. The UI can supply a snippet to define `default-forward-auth@file` for future file ownership. Explicit `traefik.middlewares` retains its legacy override behavior. `traefik.forwardauth=false` (or legacy `authelia_auth=false`, unless the new label is present) opts out; do not automatically add auth to the detected auth container itself.
- If no auth has ever been configured or detected, publish normally without automatic auth and show “automatic auth off” in the UI. Once a route is protected by the automatic default, persist that auth intent. If the required middleware, dependencies, or selected auth container become unavailable, **omit affected protected routers from newly generated configuration** (and their otherwise unused services as appropriate); never generate those routers without auth. An API request failure is not proof of absence: continue using the last known state when safe, but do not claim it is verified. Intentional disable/reset is an authenticated operation; an app restart never resets a protected route to unprotected. Explicit opt-outs and explicit middleware lists continue to follow their labels; show route-level warnings for a list that excludes default auth. File-provider routers depending on missing file resources are Traefik's responsibility and require independent status checks.
- If file and fallback names overlap across providers, use explicit `@file`/`@http` references; within the HTTP output detect collisions with container-generated router/service names. Check same-provider file duplicate names and broken dependencies using Traefik's effective API/error information where available; an effective snapshot cannot reconstruct skipped duplicates or original file boundaries.

### Traefik API and `@file` snapshots

- Deployment requirement: the app and Traefik **always** run on the same Docker daemon and the same custom Docker network with working Docker DNS resolution for container names/aliases. Discover a unique running Traefik container there, then attempt its Docker-network API address (typically `http://<traefik-name>:8080/api/rawdata`). Document and test this network assumption; if name resolution or API access fails, report the error rather than inventing an external address. Do not assume that port is available when `api.insecure` is disabled; provide optional `TRAEFIK_API_URL` and Basic-auth credentials (`TRAEFIK_API_USERNAME` plus `TRAEFIK_API_PASSWORD` or `TRAEFIK_API_PASSWORD_FILE`) for an explicitly exposed internal API router. Never store/log/display secrets. Report ambiguous discovery, unavailable API and authentication failures distinctly. No external Traefik URL or TLS is required for the agreed deployment.
- Read `/api/rawdata` as Traefik's **effective** runtime view; select only `@file` resources (across supported HTTP/TCP/UDP sections), remove runtime-only metadata (`status`, `usedBy`, `serverStatus`, `using`, etc.) with a schema-aware allowlist, retain loaded-resource errors and freshness, and store normalized snapshots in SQLite only on change. Do not store HTTP-provider dynamic output in this snapshot store. Define a bounded retention policy (proposed: last 30 distinct snapshots plus most recent verified snapshot). Keep the provider's existing last-good HTTP output separate.
- **Generate config** in the authenticated WebUI exports a selected snapshot as a single YAML dynamic-config document for manual recovery; prefer the latest verified snapshot. State plainly that this is a best-effort recreation of effective resources, **not** an exact backup of the original files, Go-template inputs, comments, skipped duplicate names, secrets, TLS certificate material, or static config. Validate a generated document against a matching Traefik version before describing it as usable. Do not claim complete restore coverage from `/api/rawdata` alone. No directory mount and no automatic restore/write to Traefik.

### Automatic auth detection and built-in templates

- Only consider **running auth containers on Traefik's Docker daemon and its custom Docker network**, using the deployment's Docker DNS name/alias. The app and Traefik share that network by requirement; for an automatically selected auth provider, its container must join it too. Match known image identities, not image/name substrings alone; document the detection rules. Priority among qualified candidates: **OAuth2 Proxy → Authentik → Authelia**. If several candidates of the same priority qualify, do not arbitrarily pick one: report ambiguity and preserve a prior safe selection. The choice becomes sticky once routes are protected, so a stop/restart or transient discovery failure does not silently remove auth; a newly higher-priority provider may replace a healthy choice only after its prerequisites are validated. Report the chosen provider and alternatives in the UI.
- Ship `oauth2proxy_auth.yml`, `authentik_auth.yml`, `authelia_auth.yml` as **alternative** built-in templates: each defines a middleware named `default-forward-auth`, never three simultaneously. No auth provider is required for users without one. No `DEFAULT_AUTH_MIDDLEWARE` setting in the target design; remove its implementation and Compose/docs wiring only when replacement behavior is verified.
- Local templates fill the ForwardAuth address with the detected container's Docker-network-resolvable name and its *container* port (OAuth2 Proxy 4180, Authentik 9000, Authelia 9091), not the published host IP/port. The supported topology **assumes** all three communicating containers share a custom Docker network with Docker DNS; document the assumption and verify name/alias availability where possible instead of pretending the app can prove Traefik's actual reachability from Docker metadata. Authentik's outpost (standalone or embedded) and OAuth2 Proxy callback/sign-in path routing may need explicit file-provider routes; document and verify those prerequisites. If they cannot be fulfilled, report an error instead of claiming a working auth setup.
- Authelia and Authentik templates define a single `forwardAuth`. OAuth2 Proxy template defines `default-forward-auth` as a chain (`oauth-signin` errors on 401 then `oauth-verify` ForwardAuth, preserving the deployment's preferred-username response header), plus `oauth2-proxy-header` only if needed by the documented flow. Its sign-in `errors.service` must be a real Traefik **service reference**: use a stable generated `@http` service that points to the detected container's network address/4180, including when it is not opted into a public router. No circular auth on the auth service. `traefik.name` / `traefik.service` overrides determine public service naming, but must not silently break this internal sign-in reference. Any existing `Oauth2proxy@file` is left untouched.
- User-defined `default-forward-auth@file` wins in full. If a file definition is confirmed removed, the app may use a complete validated local template; otherwise **omit routers whose automatic auth cannot be resolved**, never emit them unprotected. A failed API fetch is **not** proof that a file resource disappeared. Test this separately from simple Docker discovery outage handling. Legacy explicitly referenced `auth@file`/`auth@http` resources are not automatically rewritten to `default-forward-auth`; inventory them before cutover and handle their dependencies explicitly.

### Generated `default-forward-auth@http` — required output

This is a **core deliverable** of the extension, not optional. The current code only references `DEFAULT_AUTH_MIDDLEWARE` and emits `http.routers`/`http.services`; it never emits `http.middlewares`. The extension must make the HTTP provider **generate the middleware itself** from the built-in auth templates whenever `default-forward-auth@file` is absent.

Decision per refresh:

| Traefik state | Provider output | Routers without explicit middleware/opt-out reference |
|---|---|---|
| `default-forward-auth@file` loaded | No auth middlewares generated | `default-forward-auth@file` |
| Absent, qualified local auth container | Rendered template under `http.middlewares` (+ `http.services` for OAuth2 Proxy) | `default-forward-auth@http` |
| Absent, no local candidate, auth never active | Nothing generated; UI says automatic auth is off | no auth middleware |
| Absent, no local candidate, auth previously active | Nothing generated | **router omitted** (fail closed) |

Templates (`templates/oauth2proxy_auth.yml`, `templates/authentik_auth.yml`, `templates/authelia_auth.yml`) are embedded in the binary (`include_str!`), parsed with `serde_yaml`, rendered by placeholder substitution, validated, and merged into the HTTP output. Placeholders: `{{auth_host}}` = detected container's Docker DNS name; `{{auth_service}}` = generated internal sign-in service name (OAuth2 Proxy only). Ports are the containers' default internal ports. No provider-specific environment settings.

```yaml
# authelia_auth.yml
http:
  middlewares:
    default-forward-auth:
      forwardAuth:
        address: http://{{auth_host}}:9091/api/authz/forward-auth
        trustForwardHeader: true
        authResponseHeaders: [Remote-User, Remote-Groups, Remote-Email, Remote-Name]
```

```yaml
# authentik_auth.yml
http:
  middlewares:
    default-forward-auth:
      forwardAuth:
        address: http://{{auth_host}}:9000/outpost.goauthentik.io/auth/traefik
        trustForwardHeader: true
        authResponseHeaders: [X-authentik-username, X-authentik-groups, X-authentik-email]
```

```yaml
# oauth2proxy_auth.yml
http:
  middlewares:
    default-forward-auth:
      chain:
        middlewares: [oauth-signin, oauth-verify]
    oauth-verify:
      forwardAuth:
        address: http://{{auth_host}}:4180/oauth2-proxy/auth
        trustForwardHeader: true
        authResponseHeaders: [X-Auth-Request-Preferred-Username]
    oauth-signin:
      errors:
        status: ["401"]
        service: "{{auth_service}}"
        query: /oauth2-proxy/sign_in
    oauth2-proxy-header:
      headers:
        customRequestHeaders:
          X-oauth2-proxy: "true"
```

For OAuth2 Proxy the app also emits `http.services.{{auth_service}}` → `http://{{auth_host}}:4180` (Docker network address, not a published port). `{{auth_service}}` is a dedicated stable internal name derived from the container ID, avoiding collisions with a public `traefik.name`/`traefik.service` override, and is emitted **even when the container is `traefik.enable=false`**; no public router is generated unless the container opts in. Template middleware names live in the `@http` namespace, so they never collide with `oauth-verify@file` etc.; the generator rejects (and reports) collisions between template names and container-generated `@http` names. Default auth is never attached to the auth container's own router.

Expected output for the current deployment (no file default, `oauth2proxy` on `proxynet`): the 16 legacy `auth@http` routers become `default-forward-auth@http`; `oauth-verify@http` → `http://oauth2proxy:4180/oauth2-proxy/auth`; `oauth-signin@http` → dedicated `default-forward-auth-signin-<container-id-prefix>@http` → `http://oauth2proxy:4180`. Existing `Oauth2proxy@file` router/service stay untouched and still handle `/oauth2-proxy/` path callbacks.

Required code changes (missing today): typed `http.middlewares` in the provider document; capture container network names in inventory (Docker list API `NetworkSettings.Networks`) and identify Traefik's daemon/network; auth-provider detection; template embedding/rendering/validation; sign-in service emission; persisted auth state; removal of `DEFAULT_AUTH_MIDDLEWARE` (code, Compose, README) once tests pass; README documents the shared custom Docker network + Docker DNS requirement.

### Remote auth assistance

- An auth container on a different daemon or without a shared network is **not** eligible for automatic `@http` auth. When no usable `default-forward-auth@file` is present, the WebUI displays a hint and **Generate snippet** action for such a detected container. Resolve its published port from the corresponding container port and the configured Traefik-reachable upstream host; if no reachable mapping exists, explain why and do not fabricate an address.
- The generated YAML is a standalone, provider-specific `@file` definition of `default-forward-auth` for the user to paste/download into their own Traefik dynamic directory. OAuth2 Proxy's snippet also contains its full errors→service sign-in dependency; Authelia/Authentik need only ForwardAuth plus any documented outpost/path-router guidance. Validate name clashes against effective `@file` resources and warn before copying; do not assume Traefik reports source filenames or that existing same-name resources merge. After Traefik loads a valid file, the app uses **all its definitions unchanged**. No automatic file writing.

### Security, refresh and acceptance

- Keep file snapshot freshness and HTTP provider last-good freshness separately. Refresh discovery, API snapshot and auth selection in a controlled order. Retain the last complete HTTP config on transient Docker-discovery/API failures; on **confirmed** loss of required auth, generate a new config that omits affected protected routers rather than retaining a router that can no longer authenticate. Distinguish these cases in provider and UI status. Never publish a newly unauthenticated replacement. Optional provider token, WebUI session protections and network-only communication stay independent.
- Tests: three individual auth providers, all three with priority, same-priority ambiguity, none ever present, a provider stopped/removed, a vanished/broken file middleware, API offline/401/redirect, explicit middleware overrides, differing Docker hosts/networks, no published port for remote snippet, templates' transitive chain/service dependencies, snapshot normalization/export limits and retention, HTTP resource name collisions, and restart persistence. Compare provider JSON against legacy for routers/upstreams/entrypoints and equivalent auth; expect legacy `auth@http` to become either `default-forward-auth@file` or a validated `default-forward-auth@http`, **not** `auth@file`. Validate with a live Traefik v3 poll and dashboard status before cutover.

## Council review — completed; blockers resolved with user (see below)

Three read-only councillors unanimously judged the proposed extension **NOT READY** for implementation approval. The items below are review findings, **not** decisions or implemented features. Preserve the agreed automatic provider priority and ability to run without auth; do not quietly replace those requirements with mandatory confirmation or mandatory ForwardAuth.

1. **Auth-preserving migration:** live inventory now shows that all 16 current `auth@http` consumers belong to the legacy-generated HTTP provider; no file router or container label explicitly needs that legacy middleware. The preceding migration inventory and cutover gates specify the minimal change. Recheck immediately before switching. First-start behavior must distinguish a newly installed no-auth system from a protected legacy deployment: no cutover until the new provider endpoint visibly produces working protected routes. No automatic rewrite of unrelated explicit middleware references.
2. **Persisted fail-closed state machine:** user clarified that when required automatic auth is confirmed unavailable, **the affected route is not generated**. Specify when API failure/401 causes retention of the prior complete output rather than confirmed auth loss; persist intent across restarts. Distinguish unconfigured no-auth installations from previously protected installations. Do not interpret an API error as proof the file definition is absent.
3. **API and reachability contract:** obtain fixtures of this Traefik version's `/api/rawdata` response (good and bad), document how provider-qualified resources and transitive references are validated, and specify how an internal `api@internal` router is exposed independently of the HTTP provider if `api.insecure` is disabled. **Documented topology assumption:** app, Traefik and automatically selected auth container share a custom Docker network and resolve each other by Docker DNS. If this is not true, use the remote-auth snippet/file path. Report failed DNS or API access instead of silently changing provider.
4. **Snapshot fidelity and sensitive data:** rawdata may contain secret-bearing headers, URLs and password hashes. *Resolved: redact before storing (see Resolved decisions).* describe export authorization, filesystem permissions and the limitations of reconstructing YAML from the runtime view. Do not label a successful fetch an end-to-end verified restore; test supported sections/fields against a pinned version and fail visibly on unknown fields.
5. **OAuth and router correctness:** specify the internal sign-in service and chain references, callback/outpost path-router prerequisites, and auth-container self-exclusion. An explicit `traefik.middlewares` list currently overrides automatic auth: keep this documented legacy behavior and show an unprotected-route warning, unless the user approves a changed label contract. Validate generated router host collisions with file routers and template resource collisions within `@http`.
6. **Acceptance criteria:** add a machine-checked router/service comparison, a real Traefik API/dashboard status check, an end-to-end protected request through sign-in and back, failure-injection for auth/API loss, a defined observation period and a tested rollback. Current HTTP-proxy test alone is not a production-auth test.

**Resolved decisions (user, after review):**

- **Confirmed auth loss:** omit affected protected routers; transient Docker/API failures keep the last complete output without stripping auth.
- **No auth-selection setting.** `DEFAULT_AUTH_MIDDLEWARE` is removed (code, Compose, `.env.example`, README). The only override is defining `default-forward-auth` in a Traefik dynamic file. Choosing a lower-priority provider = define it in a file.
- **Automatic priority** OAuth2 Proxy → Authentik → Authelia, sticky choice, status warning, authenticated **Reset**.
- **Legacy migration:** `auth@http`/`auth@file` are not `default-forward-auth`; the generated `default-forward-auth@http` replaces the 16 legacy `auth@http` uses. Other manually configured ForwardAuth middlewares are untouched. New installs have no migration concern.
- **Topology:** app, Traefik and auto-selected auth container share one custom Docker network with Docker DNS; documented as a requirement, not probed beyond Docker metadata.
- **Docker host failures:** keep all-or-nothing last-good refresh; confirmed auth loss is a separate case.
- **Snapshots redact secrets (user decision: do not retain them).** Before storing, replace sensitive values with a `REDACTED` placeholder: `basicAuth`/`digestAuth` `users` entries, `forwardAuth.tls` key material, `headers.customRequestHeaders`/`customResponseHeaders` values whose header name looks credential-bearing (`Authorization`, `Cookie`, `*token*`, `*secret*`, `*key*`, `*password*`, `X-Api-*`), service/transport client cert/key fields, and userinfo (`user:pass@`) in any URL. Redaction happens before the SQLite write, so secrets never reach the database. **Generate config** exports the redacted document with a header comment listing every redacted path, so the user knows which values to fill in by hand; the export is still login-protected. Redaction is an allowlist-tested function with fixtures.

Implementation was explicitly authorized by the user; cutover still requires its own validation.
